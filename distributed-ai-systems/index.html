HPC / MPI Perspective

Distributed AI Systems

A non-framework-specific way to think about distributed AI through the lens of CPUs, partitions, replication, and the interconnect.

I used material from “Distributed AI Fundamentals with PyTorch” as the basis for this HPC/MPI-way of explanation for the distributed data / computational aspect. To keep the data consistent, AI systems (just as the distributed data systems do) to keep the data in partitions and replicate that data to provide reliable data access; HPC systems do not - HPC systems restart whenever there is a problem, they typically do not try to recover and they avoid this complexity. HPC / super computers use interconnect often.

1. The physical picture

Assume a cluster with:

  • Four compute nodes
  • Eight CPUs per node
  • 32 participating processes in total
  • A high-speed network such as InfiniBand
  • Each process attached to a CPU core or CPU socket
Distributed application │ Communication patterns AllReduce / Gather / Scatter │ MPI-style runtime │ Network topology and routing │ InfiniBand / RDMA / Ethernet interconnect │ CPUs, memory, NUMA, PCIe, NICs

This corresponds closely to a layered distributed-computation model:

  1. Application or framework layer
  2. Data organization layer
  3. Collective operations layer
  4. Communication and runtime layer
  5. Topology layer
  6. Physical hardware and links

The framework-specific names can be replaced with MPI concepts without changing the underlying distributed-systems ideas.

2. Processes, ranks, and world size

In an HPC program, every participating process belongs to a communicator. The communicator defines the group of processes that cooperate.

Each process has a rank, its unique identifier within the communicator; a world size, the total number of processes; a local rank, its position within a node; and a global rank, its position across the cluster.

Node 0: local ranks 0–7 global ranks 0–7 Node 1: local ranks 0–7 global ranks 8–15 Node 2: local ranks 0–7 global ranks 16–23 Node 3: local ranks 0–7 global ranks 24–31

The rank is a logical identity, not inherently a CPU identifier. Runtime placement maps ranks to cores, sockets, NUMA domains, and nodes. That mapping affects latency, bandwidth, and failure behavior.

3. Local data versus global data

Suppose the application processes a 3.2-billion-row dataset. A distributed design partitions the data so each rank performs local computation against its own share.

Rank 0: rows 0–99,999,999 Rank 1: rows 100–199,999,999 Rank 2: rows 200–299,999,999 ... Rank 31: final partition

Each rank computes a local result. The system then determines whether it needs a result from every rank, one aggregate result, the complete result on every rank, different data sent to different ranks, or a synchronized state update. That requirement determines the communication primitive.

4. Collective operations in a CPU data system

AllReduce: aggregate and replicate

AllReduce combines a value from every rank and places the final aggregate on every rank. If each process computes a local count, an AllReduce with SUM produces the global count everywhere.

The pattern is: many local values → one aggregate → replicated everywhere. It can support global row counts, error totals, convergence criteria, distributed statistics, and a shared termination decision. Optimized implementations use tree, ring, or hierarchical algorithms rather than making one process the sole bottleneck.

Reduce: aggregate to one rank

Reduce combines values from all ranks but delivers the result only to a designated root. It fits a final summary, centralized checkpoint metadata, one coordinator deciding whether processing is complete, or aggregated profiling output. Reduce followed by Broadcast is semantically equivalent to AllReduce when every rank needs the result.

Broadcast: one value to everyone

Broadcast sends data from one root rank to all other ranks. It can distribute a query plan, filter definition, lookup table, partitioning policy, job epoch, or control message. Broadcast is different from Scatter: every rank receives the same object.

Scatter: distribute different partitions

Scatter sends a different chunk to each rank. It resembles assigning partitions to workers, but it is often undesirable for rank 0 to load an entire large dataset before distributing it. For very large data, each rank commonly reads its own partition from parallel storage.

Gather: collect partitions at one rank

Gather sends data from every rank to one root. It works for per-rank metrics, error summaries, small result sets, and diagnostics. It becomes dangerous when the result is large because the root becomes both a memory bottleneck and a network hotspot.

AllGather: collect and replicate

AllGather collects data from all ranks and gives the complete concatenated result to every rank. It is useful when every process needs a global view, but replication across all ranks makes it expensive for large datasets.

ReduceScatter: aggregate and partition

ReduceScatter reduces corresponding values across ranks and gives each rank only its assigned portion of the reduced result. The pattern is: many distributed inputs → aggregate → distributed output. It supports partitioned aggregations, ownership-based updates, distributed histograms, and per-shard statistics without creating a complete copy everywhere.

All-to-All: exchange personalized partitions

All-to-All allows every rank to send different data to every other rank. This is the communication pattern behind hash redistribution, range repartitioning, distributed joins, global sorts, and large-scale shuffles.

It is potentially the most communication-intensive collective because every rank may communicate with every other rank. At scale, network and memory pressure can dominate computation.

5. Data parallelism versus partitioned data processing

The data-parallel pattern is straightforward: every process has the same program and configuration, each process owns a different data partition, each computes locally, and processes exchange only required summaries or intermediate data.

local computation ↓ small collective communication ↓ more local computation

The less data that crosses the interconnect, the better the scaling tends to be.

6. Replicated versus sharded state

Replicated state

Every rank stores a complete copy. Access is simple and local, but memory is duplicated and updates must be synchronized.

Sharded state

Each rank stores only a portion. Total state can exceed one node’s memory, but remote lookups, rebalancing, and failure handling become more complex.

A sharded distributed index illustrates the trade-off. If a process receives a key owned by another rank, it can send the request to the owner, replicate enough index state locally, or redistribute the original data so requests become local.

7. Bucketing and message efficiency

Many small messages are usually less efficient than fewer larger messages. Every message carries fixed runtime, NIC, protocol, scheduling, and synchronization overhead.

10,000 messages × 4 KB → 100 messages × 400 KB

The same principle applies to distributed data systems: batch remote reads, coalesce small records, aggregate before sending, use partition-aware buffering, avoid per-row RPCs, and prefer bulk exchange during a shuffle. Excessively large messages can still increase latency, so the practical goal is balanced batching.

8. Communication is shaped by the interconnect

CPU and memory configuration alone does not determine performance. A transfer may cross a CPU memory bus, a NUMA boundary, PCIe, a network interface, the physical fabric, and the receiving node’s PCIe and memory hierarchy.

Intra-node communication

Within a node, processes may communicate through shared memory, CPU caches, NUMA memory, or PCIe-connected devices. This is usually lower latency than inter-node communication, although crossing NUMA sockets can still be expensive.

Inter-node communication

Between nodes, data travels through network interface cards, switches, and fabric links. InfiniBand with RDMA can reduce CPU involvement and latency. Ethernet is common and flexible, with performance depending on its configuration.

Topology

Fat-tree, dragonfly, torus, mesh, and other topologies determine hop count, oversubscription, link contention, all-to-all behavior, and the effect of failures on alternate routes.

9. Synchronization and the “hung job” problem

Collectives are usually collective in the strict sense: every participating rank must call the operation in the expected order.

Rank 0: AllReduce → Broadcast → Gather Rank 1: AllReduce → Broadcast → Gather Rank 2: AllReduce → Broadcast → Gather

If one rank skips the AllReduce, the others can wait indefinitely. The network may be healthy; the distributed program is inconsistent.

Debugging should proceed down the stack: confirm every rank is alive; verify that every rank entered the same collective; check communicator, data shape, and message size; verify process placement; then inspect interconnect reachability, congestion, and fabric configuration.

10. Overlap computation and communication

A distributed application performs best when communication overlaps useful computation.

Compute partition 0 ──┐ ├── exchange partition 0 Compute partition 1 ──┘ Compute partition 2 ──┐ ├── exchange partition 2 Compute partition 3 ──┘

Instead of waiting for all local work to finish, an application can send completed partitions, continue computing other partitions, receive remote data, and synchronize only when the next phase needs it. This applies to distributed matrix operations, stencil computations, partitioned joins, iterative solvers, graph algorithms, and simulations.

12. The most important conceptual translation

A high-level distributed operation is implemented by a stack of increasingly lower-level mechanisms, and performance or failure can originate at any layer.

Application: distributed aggregation or shuffle ↓ Logical operation: AllReduce, Gather, Scatter, All-to-All ↓ Runtime: MPI collective implementation ↓ Topology: rank placement, NUMA layout, network fabric ↓ Transport: shared memory, TCP, RDMA ↓ Hardware: CPU cores, memory bandwidth, NICs, switches

If an aggregation is slow, possible explanations include too much data being reduced, poor partitioning, too many small messages, a root bottleneck, NUMA misplacement, network oversubscription, a topology-unfriendly algorithm, or insufficient overlap between computation and communication.

The central lesson is not specific to a Python library. It is that distributed computation must be understood across the application, communication, runtime, topology, transport, and hardware layers. Distributed AI and distributed data platforms accept the complexity of partitioning, replication, and coordination when reliable access and continued service are part of the objective. HPC systems often optimize for maximum throughput for a bounded computation and rely on restarting the job when the computation fails.
