Remote Coding Agent Platform on Railway

A deployment and operational playbook for securely provisioning isolated, browser-accessible coding environments with automated repository bootstrap, reverse-proxy access, and managed lifecycle control.

This document reformats the supplied playbook into an implementation-oriented reference. It retains the original architectural intent—isolated sandboxes, secure browser access, agent tooling, and Railway-backed orchestration—while clarifying the control plane, security boundaries, and operating model.

1. System overview and architecture

The platform dynamically provisions, manages, securely proxies, and decommissions isolated cloud sandboxes on Railway. Each sandbox is an ephemeral development environment prepared with coding-agent tooling and a browser-accessible IDE. The intended workflow is direct: a user requests an environment, the control plane creates it, the sandbox bootstraps a target repository, and the user works through a protected browser session.

Frontend control plane

React and Vite application for requesting environments, observing status, and opening IDE sessions.

Backend API and orchestrator

Express REST API, Drizzle ORM, PostgreSQL persistence, and Railway GraphQL mutations for lifecycle operations.

Reverse proxy layer

Terminates HTTP and upgrades WebSockets, bridging authenticated browser sessions to private internal services.

Sandbox environment

Linux AMD64 container running code-server, Node.js 22, Git, coding-agent CLIs, and persistent volume mounts.

2. Sandbox container and bootstrap

The sandbox entrypoint should establish a predictable working directory, hydrate only the environment state needed by the session, and fail fast when bootstrap is incomplete.

#!/usr/bin/env bash
set -euo pipefail

WORKSPACE_DIR="/home/sandbox/workspace"
mkdir -p "$WORKSPACE_DIR"
cd "$WORKSPACE_DIR"

# If repository credentials and a source repository are present:
#   clone or fetch the target branch into the mounted workspace.
# Otherwise: start an empty workspace.

Repository credentials must be injected as short-lived runtime secrets, not written to logs, images, or the repository checkout. The bootstrap path should support a configured target branch, safely handle an existing persistent clone, and use a bot identity for commits or pull requests where required.

Container baseline

The supplied playbook uses a Node.js 22 Debian-based image, installs Git, SSH tooling, certificate support, process utilities, code-server, and the approved coding-agent CLIs. The image should contain tooling; credentials and repository-specific configuration should arrive only at runtime.

LayerResponsibility
Image buildRuntime, code-server, Git, supported CLIs, entrypoint, non-secret defaults.
Volume mountDurable workspace and optional repository cache across sandbox restarts.
Runtime secretsRepository access, model-provider keys, Railway token, JWT signing secret.
EntrypointWorkspace creation, repository bootstrap, branch selection, IDE startup.

3. Orchestration and persistence

The control plane records the relationship between a user-facing sandbox request and the Railway resources created for it. A minimal record includes an internal identifier, owner or organization identity, repository URL, Railway project and environment identifiers, service identifier, status, and timestamps.

Sandbox record
  id                UUID / primary key
  owner_id          authenticated user or organization
  repository_url    source repository
  railway_project   Railway project reference
  railway_service   sandbox service reference
  status            provisioning | active | failed | retiring | retired
  created_at        lifecycle timestamp

Railway lifecycle actions are executed through the API layer’s GraphQL client. Keep API-specific mutations behind an adapter so the REST surface remains stable if deployment mechanics change.

4. Security and access boundaries

The critical boundary is between the public browser and the private sandbox network. Sandboxes should not be exposed as arbitrary public services. A proxy validates the browser session, resolves the authorized sandbox, and forwards only to the permitted internal service address.

Browser session │ JWT / session cookie ▼ API authorization ──► signed, short-lived proxy context │ │ └──────────────► reverse proxy validates target │ ▼ <service-name>.railway.internal:8080

Use an HttpOnly, secure session cookie with an appropriate SameSite policy; keep JWT signing material in the secret store; enforce ownership checks on every sandbox read, launch, and retirement operation; and validate host and path construction before proxying. Repository and provider credentials must never transit to the browser.

5. API surface and lifecycle

The backend exposes a small lifecycle API. Its contract should remain resource-oriented and auditable.

OperationPurpose
Create sandboxValidates repository input, records a provisioning request, and creates the Railway service.
Get sandboxReturns owned sandbox state and a safe status view for the control plane.
Launch IDECreates or validates a proxy-access context for the browser session.
Retire sandboxStops or deletes the service, records terminal status, and cleans temporary resources.
Health checkVerifies API and database reachability for platform monitoring.

Lifecycle handling should be asynchronous from the user’s perspective: return a provisioning state promptly, poll or stream status updates, and make transitions explicit. A failed provisioning attempt should retain sufficient diagnostic state for support without leaking secrets or raw provider responses.

6. Frontend control plane

The frontend is a small operational console rather than a general-purpose IDE shell. It provides a create-environment flow, cards or rows for existing sandboxes, clear status semantics, and an IDE launch action only when the service is ready.

Create flow

Collect repository URL and branch, validate server-side, then show the provisioning state immediately.

Status model

Use explicit badges for provisioning, active, failed, retiring, and retired rather than inferring state from UI behavior.

IDE launch

Open only an authorized proxy route; never surface private Railway hostnames or tokens in the browser UI.

Failure path

Show an actionable message and a safe correlation identifier; retain deeper diagnostics in server-side logs.

7. Build, deployment, and operations

Build the sandbox image for the required Linux AMD64 target, publish it through the deployment pipeline, apply database migrations before the API rollout, and deploy the frontend against the API’s stable public origin.

# Representative deployment sequence
build sandbox image for linux/amd64
publish image to configured registry
apply database migrations
release API and orchestration service
release frontend control plane
verify health endpoint and sandbox create → launch → retire flow

Operationally, instrument provisioning duration, active sandbox count, proxy connection failures, container exit codes, API error rates, and retirement success. Establish a retention policy for sandboxes and their attached volumes so idle environments do not become an unbounded cost or data-retention risk.

8. Production-readiness checklist

AreaMinimum control
IdentityAuthenticated users, ownership checks, and server-side authorization on every lifecycle action.
SecretsRuntime injection only; no credential values in images, logs, browser responses, or committed source.
ProxyingShort-lived authorization context, target allowlist, HTTP and WebSocket support, and audit logging.
IsolationOne sandbox per logical request with bounded resources and defined network access.
ObservabilityHealth checks, lifecycle events, structured logs, provider correlation IDs, and metrics.
RecoveryIdempotent lifecycle operations, deterministic retirement, and documented handling for partial provisioning failures.

Conclusion

The platform’s value comes from separating the experience of a self-service coding workspace from the operational complexity of transient infrastructure. The frontend remains deliberately small; the backend owns lifecycle, identity, and persistence; the proxy enforces a narrow access boundary; and each sandbox receives only the tooling and credentials needed for its configured task.
